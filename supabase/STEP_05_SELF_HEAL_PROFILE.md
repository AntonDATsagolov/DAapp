# DAapp — самостоятельное восстановление отсутствующего профиля

При входе может появиться «Профиль не найден», если аккаунт существовал ещё до создания таблицы profiles или его запись отсутствует.

## Один раз в Supabase

1. Перейдите в Supabase → **SQL Editor** нужного проекта.
2. Откройте файл `supabase/migrations/003_ensure_own_profile.sql` и выполните его содержимое.
3. Обновите страницу `https://antondatsagolov.github.io/DAapp/client-app/`.
4. Если приложение сообщит, что профиль по-прежнему недоступен, проверьте RLS `profiles`: пользователю нужен `SELECT` своей строки и `auth.uid() = id`. Не отключайте RLS.

## Почему это безопаснее, чем разрешить INSERT всей таблицы

Функция принимает **ноль аргументов** и получает ID исключительно из подписанной сессии через `auth.uid()`. Она может добавить **только одну** запись — для текущего пользователя, причём всегда с ролью `client`. При наличии записи ничего не меняет. У `anon` и `PUBLIC` нет права выполнять функцию. Функция создана с `security definer` и пустым `search_path`, а имена таблиц и функций указаны со схемой.

Клиентское приложение продолжает читать профиль через RLS. Функция не раскрывает пользователей и не выдаёт повышенных ролей.

## Если в Supabase уже был применён SQL 002

Это не мешает миграции 003. Если профиль уже существует, функция ничего не изменит.

## Важно для будущих пользователей

Если `daapp_auth_user_created` не был установлен, триггер для новой регистрации всё равно потребуется проверить отдельно. Миграция 003 помогает существующим авторизованным пользователям; она не меняет триггеры.

Этот SQL **не запускается из GitHub Actions** и не устанавливается автоматически при публикации сайта.
