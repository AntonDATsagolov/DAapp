# DAapp: исправление «Профиль не найден»

**Проблема:** Supabase Auth подтвердил вход пользователя, но запрос `profiles` вернул пустой результат.

Возможны две причины:
1. Пользователь уже существовал, когда была создана таблица `profiles`. Триггер для новых пользователей не создаёт старые строки.
2. Строка существует, но пользователь не видит её из-за отсутствия разрешений `SELECT` или ошибки в RLS.

## Шаг 1. Восстановление недостающих профилей

1. Откройте Supabase Dashboard → SQL Editor.
2. Скопируйте содержимое файла `supabase/migrations/002_backfill_existing_profiles.sql` и нажмите Run.
3. Скрипт добавляет **только отсутствующие** профили с ролью `client`; существующие роли, имена и телефоны остаются без изменений.
4. Посмотрите на `users_still_missing_profiles`: ожидаем `0`. Запомните `daapp_new_user_trigger_exists` (true/false).
5. Обновите страницу DAapp с текущим входом. Повторная регистрация не требуется.

## Шаг 2. Если ошибка осталась

Проверьте в Supabase SQL Editor без отправки пользовательских данных в чат:

```sql
select relrowsecurity as rls_enabled
from pg_class
where oid = 'public.profiles'::regclass;

select policyname, cmd, roles, qual
from pg_policies
where schemaname = 'public' and tablename = 'profiles';
```

Политика чтения должна разрешать пользователю видеть **только свою** строку по `(select auth.uid()) = id`. Также должны быть выданы нужные права `SELECT` для `authenticated`; в базовой миграции `001_profiles_initial.sql` они ограничены перечисленными колонками.

Если `daapp_new_user_trigger_exists` = false, автоматическое создание профиля для **будущих** пользователей отсутствует. Вначале проверьте, какие триггеры уже созданы на `auth.users`. Не добавляйте второй без проверки.

**Важно:** SQL выполняется в Supabase SQL Editor. GitHub Actions не изменяет вашу базу автоматически. Никогда не вставляйте `sb_secret_*` в браузер или репозиторий.
