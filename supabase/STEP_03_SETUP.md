# DAapp — шаг 3: профили и доступ

Эта миграция предназначена **только для новой базы без таблицы `public.profiles`**. Если таблица уже существует, SQL остановится с ошибкой до внесения изменений. Не удаляйте таблицу для обхода проверки.

## Перед запуском
1. Откройте Supabase → SQL Editor.
2. Проверьте в Table Editor, существует ли `public.profiles`. Если да — **не запускайте** эту миграцию; сначала нужно сравнить существующие поля и RLS.
3. Если таблицы нет, откройте `supabase/migrations/001_profiles_initial.sql`, проверьте код и запустите его в SQL Editor.
4. В Authentication → URL Configuration укажите разрешённые адреса возврата для входа по e-mail.
5. Создайте тестового пользователя и проверьте, что появилась запись в `profiles` с ролью `client`. Проверка авторизации из веб-приложения ещё не выполнена.

## Ограничения безопасности
- Клиент читает только свой профиль.
- Клиент меняет только `full_name` и `phone_number` (с помощью ограниченных SQL GRANT).
- Роли `driver` и `business_owner` не назначаются через PWA: позже добавим безопасную административную процедуру.
- Прямые вставки и удаления профилей из клиентского PWA не разрешены.
- Таблицы `businesses`, `catalog_items`, `taxi_orders` пока не менялись. Для них потребуются отдельные RLS-политики.
- Данная миграция не проверяет другие ранее созданные политики и не переносит существующих пользователей.

**Не добавляйте `sb_secret_*` в GitHub или в исходники.** Ранее раскрытый secret key необходимо отозвать.
