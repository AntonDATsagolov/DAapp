# DAapp — Шаг 16. На работе / Не на работе

## Как работает

**Предприниматель:** после одобрения заявки администратором и публикации
организации на карте её владелец видит в бизнес-кабинете переключатель
**«На работе / Не на работе»**. Для нескольких опубликованных организаций
у одного пользователя — отдельный переключатель у каждой. Состояние
хранится в Supabase и переживает закрытие страницы и перезапуск телефона.
Новое место сначала отмечено **«Не на работе»**, пока владелец не нажмёт
переключатель. Владелец должен переключать статус вручную — расписание
и автоматический таймер пока не реализованы.

**Водитель:** в подтверждённом водительском кабинете две старые кнопки
«Выйти на линию» и «Завершить смену» заменены одним переключателем.
Он вызывает прежнюю, защищённую Supabase функцию
`daapp_driver_set_online(boolean)`. Кандидат с ожидающей или
отклонённой заявкой переключать статус не может.

**Житель / гость:** на карте рядом с опубликованными организациями
показывается зелёное **«На работе»** или серое **«Не на работе»**, а
цвет метки также соответствует выбранному статусу. Если SQL 012 ещё
не выполнен, карта остаётся работоспособной и показывает
**«Статус работы не указан»** вместо выдуманного состояния.

В категории **«Такси»** отображается безопасная общая цифра:
сколько **подтверждённых** водителей поставили статус «На линии»,
исключая заблокированные аккаунты. Сами водительские записи,
номера телефонов, госномера и координаты **не раскрываются**.
Опубликованные организации такси на карте и индивидуальные водители —
разные сущности. Публичная цифра **не гарантирует возможность
заказать машину**: реальные заявки, назначение водителя, расчёт цены,
геопозиция и чат всё ещё в разработке.

## Включение в Supabase

GitHub Pages публикует интерфейсы, но **не выполняет SQL автоматически**.

1. Убедитесь, что SQL 001–011 выполнены.
2. Откройте SQL Editor того же рабочего проекта Supabase.
3. Выполните **ОДИН РАЗ** файл
   [012_business_driver_work_status.sql](../supabase/migrations/012_business_driver_work_status.sql).
4. Проверьте в бизнес-кабинете под **реальным подтверждённым владельцем**
   опубликованной организации, что его организация появилась.
5. Переведите её в «На работе». Откройте карту жителя, обновите
   страницу — проверьте цвет и статус. Верните «Не на работе».
6. Под одобренным водителем включите переключатель «На работе».
   У другого пользователя в категории «Такси» увеличится число
   водителей на линии. Выключите — число уменьшится.
7. Проверьте, что чужую организацию нельзя включить из другого аккаунта.

SQL 012 не требует удаления или повторного создания существующих таблиц,
не меняет пользователей и сохраняет RLS. Для статуса опубликованной
организации используется связь одобренной заявки с записью в карте
через `daapp_moderation_log`. **Организации, созданные вручную в
SQL Editor без этой связи, нельзя переключать из бизнес-кабинета**:
нужна отдельная безопасная процедура назначения владельца после проверки.

## Технические детали

- В `map_places` новые поля `is_working boolean not null default false`
  и `work_status_changed_at`.
- Для владельца: `daapp_business_my_workplaces()` и
  `daapp_business_set_working(place_id, boolean)`, обе только
  аутентифицированным клиентам; внутри ещё раз проверяются реальное
  владение, одобрение и публикация.
- Для жителей: `daapp_public_available_drivers()` возвращает
  **только целочисленное количество**, может вызываться без входа,
  а таблица `driver_registrations` остаётся закрытой для публики.
- Переключатели обновляются лишь после ответа сервера, при ошибке
  возвращаются в предыдущее состояние.

Изолированные PostgreSQL-интеграционные тесты проверяют RLS,
запрет чужих переключений, доступ анонимного жителя к статусу,
подтверждённых водителей и скрытие частных водительских данных.
Они не заменяют реального теста рабочего Supabase.
