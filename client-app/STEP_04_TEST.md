# DAapp — шаг 4: проверка личного профиля

Обновлены `client-app/index.html` и `client-app/profile.js`.
Секретные ключи не используются.

## Как проверить
1. В Supabase проверьте, что таблица `public.profiles` имеет колонки `id`, `full_name`, `phone_number`, `role`, `driver_vehicle_type`. Для пользователей должны быть включены RLS-политики и разрешено изменение **только** `full_name` и `phone_number`.
2. В Authentication → Providers → Email разрешите вход по электронной почте.
3. В Authentication → URL Configuration → Redirect URLs добавьте `http://localhost:8000/client-app/` для локального теста. В дальнейшем добавьте реальный HTTPS-адрес приложения.
4. Запустите из корня репозитория локальный HTTP-сервер (`python3 -m http.server 8000`) и откройте `http://localhost:8000/client-app/`. Открывать через `file://` нельзя.
5. Введите свой e-mail, откройте письмо и перейдите по ссылке.
6. В разделе «Мой профиль» введите имя и телефон, нажмите «Сохранить профиль». После перезагрузки значения должны сохраниться.
7. Проверьте кнопку «Выйти».

## Если профиль не найден
Миграция шага 3 автоматически создаёт записи только для **новых** пользователей Supabase Auth. Если пользователь уже существовал до миграции, создайте его профиль вручную через доверенную административную процедуру. Не открывайте право `INSERT` для клиентского приложения ради обхода ошибки.

## Безопасность
Роль показана только для чтения. Запрет изменения роли должен обеспечиваться базой (RLS **и** ограничением SQL GRANT), а не только скрытием поля на экране. Не используйте `service_role` или `sb_secret_*` в JavaScript/HTML.

## Статус
Код закоммичен в рабочей ветке. Настоящий вход, чтение и сохранение данных требуют ручной проверки в вашем Supabase; удалённые данные из ChatGPT не изменялись.
