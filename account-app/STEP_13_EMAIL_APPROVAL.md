# DAapp — Шаг 13. Регистрация по e-mail, ручное одобрение, телефон и аватар

> **Обновление:** Ручное одобрение каждого жителя — предыдущий сценарий. После установки SQL 010 обычные пользователи с подтверждённым e-mail получают базовый доступ автоматически. Бизнес и водители проходят отдельную проверку. См. [Шаг 14](../admin-app/STEP_14_CONTROL_CENTER.md).


**Ссылка регистрации:** https://antondatsagolov.github.io/DAapp/account-app/  
**Админка:** https://antondatsagolov.github.io/DAapp/admin-app/  
**Контакты:** https://antondatsagolov.github.io/DAapp/directory-app/

## Как работает

1. Человек вводит **логин, пароль, e-mail, телефон, возраст, житель/гость**. Выбирает аватар (загрузить его можно после входа по ссылке). Публикация телефона — **отдельная добровольная галочка**, по умолчанию выключена. Для лиц младше 18 лет номер не публикуется.
2. Supabase отправляет письмо с подтверждением e-mail. Убедитесь, что это письмо доставляется; без подтверждения администратор не может одобрить заявку.
3. В таблице `daapp_account_applications` находится запись со статусом **pending**. Техническая сессия Supabase Auth после подтверждения почты возможна, но **закрытые таблицы защищены RLS** и пользователю доступны только статус заявки и загрузка личного фото.
4. Администратор открывает **Новые пользователи DAapp**, проверяет e-mail, телефон (пока без SMS), тип аккаунта, аватар и нажимает **Одобрить** или **Отклонить**. Роль водителя или предпринимателя не выдаётся автоматически.
5. После одобрения пользователь входит по e-mail+паролю; по логину+паролю — только после отдельной настройки защищённой серверной функции.
6. Публичная карта работает без регистрации. После одобрения у аккаунта обычный доступ жителя/гостя, а водитель и владелец бизнеса могут получать дополнительные статусы без отдельного аккаунта.

## Включить регистрацию — обязательные шаги

### 1. SQL 009

В Supabase Dashboard откройте **SQL Editor → New query**. Предварительно должны быть выполнены миграции 001–007, в том числе 006 (админы) и 007 (водители). SQL 008 необязателен. Выполните содержимое:

`supabase/migrations/009_email_approval_directory.sql`

Ссылка: https://github.com/AntonDATsagolov/DAapp/blob/main/supabase/migrations/009_email_approval_directory.sql

Миграция создаёт новый список заявок, защищённый реестр логинов, правила доступа, очередь администратора и публичное хранилище аватаров `daapp-avatars`. Все созданные ПОСЛЕ применения миграции аккаунты сначала получают **pending**, включая обходы формы через обычный Supabase signup. Аккаунты, созданные ДО этой миграции, сохраняют прежний доступ. **Повторно выполнять SQL 009 нельзя.** Если SQL 008 раньше не был выполнен, после 009 не запускайте его (таблица уже существует).

### 2. E-mail подтверждение в Supabase

Откройте Authentication → Providers → Email:
- **Enable Email provider — ON**.
- **Confirm email — ON**.
- Authentication → General → **Allow new users to sign up — ON**.
- Authentication → URL Configuration → Redirect URLs: добавить ровно
  `https://antondatsagolov.github.io/DAapp/account-app/`
- Site URL может указывать на `https://antondatsagolov.github.io/DAapp/`.

Для пробного запуска встроенный отправитель Supabase имеет лимиты и может отправлять письма только на ограниченный круг адресов. Для реальных пользователей понадобится собственный SMTP. **Отсутствие SMS-провайдера не влияет на регистрацию через e-mail.**

### 3. Администратор

Старый администратор из таблицы `public.daapp_admins` может войти по прежней почтовой ссылке в админку. В появившемся блоке **Новые пользователи DAapp** видны логин, почта, номер, категория житель/гость, факт подтверждения почты и аватар. Проверьте данные и отметьте подтверждение проверки перед одобрением.

Если администратор ещё не назначен, это отдельное доверенное действие через SQL Editor, только для вашего собственного e-mail:

```sql
insert into public.daapp_admins(user_id)
select id from auth.users where email = 'ВАШ_ДЕЙСТВУЮЩИЙ_EMAIL'
on conflict(user_id) do nothing;
```

Не вводите в поле e-mail чужой адрес и не раздавайте роли администратора пользователям через браузер.

### 4. Логин и пароль

**Вход по e-mail + паролю** работает штатно через Supabase Auth после подтверждения e-mail и решения администратора. До одобрения можно войти только в экран статуса заявки; серверные RLS ограничивают остальные функции.

**Вход по отдельному логину + паролю** требует развернуть уже подготовленную функцию
`supabase/functions/daapp-username-login/index.ts` в проекте Supabase с именем `daapp-username-login`. Она на сервере сопоставляет логин и подтверждённую почту, проверяет решение администратора и передаёт пароль только Supabase Auth. Без этого маршрута пользователь может войти **по e-mail**, а не по логину.

В Dashboard → Edge Functions выберите создание функции через редактор, если доступно, вставьте код, задайте имя `daapp-username-login`. Для этого маршрута нужно выключить JWT verification: перед входом у пользователя ещё нет токена. Секреты `SUPABASE_SERVICE_ROLE_KEY` и `SUPABASE_ANON_KEY` **никогда не помещайте в GitHub Pages или HTML**. Для публичного запуска настройте ограничения попыток входа, защиту от ботов и восстановление пароля.

Если Dashboard не даёт развернуть функцию в редакторе, выполните локально через Supabase CLI:
```bash
supabase login
supabase link --project-ref huajxbmapmlprcyytsvu
supabase functions deploy daapp-username-login --no-verify-jwt
```

### 5. Телефон и аватар

Телефон запрашивается **для звонков, но НЕ верифицируется через SMS**. Прямой номер пользователя не должен показываться всем автоматически. Только после его добровольного согласия, подтверждения аккаунта администратором и при возрасте 18+ он появится в справочнике. Справочник доступен только одобренным вошедшим пользователям. Человек может позже скрыть номер в настройках собственного профиля.

Аватар: JPG/PNG/WebP, не более 1,5 МБ. На экране регистрации можно выбрать фото, но **до подтверждения e-mail оно не загружается**; после входа нужно выбрать и сохранить его в личном кабинете. Файлы лежат в публичном бакете Supabase с непредсказуемым именем и ограничением загрузки в собственную папку. Изображения публичны для любого, кто знает URL; не загружайте документы или приватные фотографии.

### 6. Мини-тест без настоящих SMS

1. Откройте регистрацию в приватном окне.
2. Укажите новый e-mail, придуманный логин, пароль, свой контактный номер, возраст и «Житель» или «Гость».
3. Отправьте заявку и подтвердите e-mail через письмо.
4. В личном кабинете появится **Ожидает одобрения**. Сохраните аватарку.
5. Зайдите в админку своим прежним аккаунтом → **Новые пользователи DAapp** → **Одобрить**.
6. Вернитесь в кабинет нового пользователя, обновите статус, откройте DAapp.
7. Проверьте вход **по e-mail и паролю**. После развёртывания функции проверьте вход **по логину и паролю**.
8. Для звонков включите добровольную публикацию телефона и проверьте справочник под другим одобренным аккаунтом.

## Что нельзя считать проверенным автоматически

GitHub CI прогоняет сценарий на искусственных учётных записях в отдельной базе PostgreSQL. Это НЕ означает, что письмо реально дошло, SMS-номера подтверждены, SQL 009 установлен в рабочей базе или что Edge Function уже развернута в Supabase. Эти этапы требуют проверки на реальном проекте.

В целях защиты пользователей телефоны и аватары не сохраняются в браузерном локальном хранилище и не доступны без соответствующего разрешения в базе.
