# DAapp — Шаг 12: единый аккаунт человека

## Почему не три отдельных пользователя

Единый `auth.users.id` связывает все сервисы. После регистрации человек всегда может пользоваться DAapp как житель/гость. Одновременно он вправе:
- иметь подтверждённую анкету водителя в `driver_registrations`;
- подавать и получать одобрение для своих организаций в `place_submissions`.

Это **не эксклюзивные роли**. Старое `profiles.role` остаётся `client` и не повышается через браузер. Наличие подтверждённой анкеты водителя или заявки на организацию добавляет возможности, а не создаёт второй аккаунт. Администратор — отдельное разрешение `daapp_admins`.

## Экран регистрации

https://antondatsagolov.github.io/DAapp/account-app/

Новый пользователь вводит:
1. уникальный логин (4–24 символа, латинские буквы, цифры и подчёркивание, начинается с буквы);
2. номер телефона Казахстана `+7XXXXXXXXXX`;
3. возраст на момент регистрации (в этой версии самостоятельная регистрация с 13 лет; возраст пока указан самим пользователем, не подтверждён документом);
4. пароль 10–72 символа и подтверждение пароля;
5. одноразовый SMS-код, отправленный через Supabase Auth.

Номер реально считается подтверждённым **только после** успешного вызова `auth.verifyOtp({phone, token, type:'sms'})`. SQL `daapp_claim_username` проверяет `auth.users.phone_confirmed_at` — нельзя самостоятельно выставить признак подтверждения в браузере. Возраст хранится отдельно от телефона, как `age_at_registration`, не автоматически пересчитывается каждый год.

Пароль хранится **только в Supabase Auth**. В таблице DAapp пароля нет. Не надо вводить настоящий номер телефона до подключения и проверки SMS-провайдера.

## Настройка базы — один раз

Если выполнены миграции 001–007, откройте **только**:
`supabase/migrations/008_unified_member_accounts.sql`

Выполните через Supabase Dashboard → SQL Editor. Новый SQL:
- создаёт `daapp_member_accounts`;
- выдаёт чтение только владельцу по RLS;
- разрешает привязку логина только после настоящего SMS-подтверждения;
- запрещает клиенту узнавать чужой телефон по логину;
- не удаляет и не меняет существующие аккаунты, роли и заявки.

Если SQL 007 ещё не был применён, сначала завершите его настройку. Миграцию 008 не надо запускать повторно.

## Настройка SMS и входа по паролю

Supabase → **Authentication → Providers → Phone**: включить вход с номером телефона и **настроить реального SMS-провайдера**, способного доставлять SMS на казахстанские номера. Проверить rate limits, CAPTCHA и бюджет сообщений. После включения пользователь сможет войти по **телефону + паролю** через `auth.signInWithPassword`.

Supabase → Authentication → Settings: Allow new users to sign up = enabled.

**Вход по уникальному текстовому логину** не является встроенной функцией Supabase. Для него в репозитории подготовлен серверный обработчик:
`supabase/functions/daapp-username-login/index.ts`

Его нужно **отдельно развернуть** в Supabase Edge Functions под именем `daapp-username-login`, с отключённой проверкой JWT именно на этом маршруте (гость ещё не имеет JWT). Серверу нужны стандартные переменные окружения `SUPABASE_URL`, `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`. Секретный ключ используется исключительно внутри серверной функции, в HTML/GitHub Pages его нет. Функция извлекает телефон по закрытой таблице и затем проверяет пароль через штатный Supabase Auth, не обрабатывая пароль сама и не отдавая чужие телефоны. При ошибке возвращается одинаковое сообщение, чтобы не раскрывать наличие логина.

**Пример развёртывания локальным Supabase CLI:**

```bash
supabase login
supabase link --project-ref huajxbmapmlprcyytsvu
supabase functions deploy daapp-username-login --no-verify-jwt
```

Эти команды **не выполнены автоматически через GitHub**. После публикации функции и настройки SMS пользователь сможет войти как по уникальному логину, так и по телефону и паролю.

Перед широким публичным запуском также нужны контроль частоты попыток по логину/IP, CAPTCHA/защита от ботов, проверка конфигурации MFA и процедура восстановления доступа: мобильные номера могут переходить к другим владельцам. Нельзя считать один SMS-код достаточной мерой для всех финансовых действий.

## Старые пользователи

Старый вход по Email Magic Link остался для **существующих** аккаунтов (`shouldCreateUser:false`), чтобы не потерять историю. В кабинете единого аккаунта предусмотрена попытка привязать телефон через SMS `phone_change`, затем установить пароль и закрепить логин. Если Supabase потребует повторно подтвердить пароль или сеанс, пользователь увидит ошибку и сохранит возможность прежнего входа по e-mail.

**Не создавайте новый аккаунт с тем же номером для уже существующего email-аккаунта**, сначала привяжите телефон к текущему.

## Особенности и ограничения

- Учетная запись взрослого/несовершеннолетнего не подтверждает право работать таксистом. Удостоверение и право осуществлять перевозки проверяет администратор отдельно.
- Представитель бизнеса и водитель могут одновременно заказывать товары как обычные жители — ничего переключать между отдельными профилями не нужно.
- Управление несколькими организациями с разными сотрудниками, возврат доступа и профессиональные разрешения будут расширяться позже.
- Истинное положение и возраст человека автоматически не подтверждаются. Не используйте указанный возраст как доказательство совершеннолетия.
- Без настройки SMS и SQL 008 новый сценарий регистрации в рабочей базе **не завершится**; старые пользователи могут продолжать вход по e-mail.
- Регистрация логина не предполагает публикацию номера телефона. Логин в `member_accounts` доступен только самому пользователю и доверенному серверному обработчику.
