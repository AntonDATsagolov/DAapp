# DAapp — Шаг 15. Один адрес, один аккаунт, несколько рабочих режимов

## Главное

**Единственный адрес для пользователей**: https://antondatsagolov.github.io/DAapp/

Не нужно сохранять три ссылки. Стартовая страница открывает единый аккаунт: если пользователь ещё не вошёл, показывает регистрацию/вход; если сессия сохранена — запрашивает у Supabase перечень допущенных режимов и открывает последний. Пароли не хранятся в GitHub Pages; Supabase Auth поддерживает восстановление пользовательской сессии между перезапусками браузера. Если сессия истекла, достаточно войти снова. Последний режим хранится **на сервере** в таблице `public.daapp_member_navigation` и сохраняется при смене телефона.

**Один человек = один Auth ID**, независимо от количества допущенных режимов.

- **Житель / покупатель:** базовый режим после подтверждения e-mail и активации аккаунта. Публичная карта доступна даже без входа. Реальные заказы покупателей пока не подключены.
- **Предприниматель:** режим доступен лишь при наличии хотя бы одной **одобренной** заявки в `place_submissions` этого пользователя. Подача заявки и публикация организации не означают готовность каталога товаров или заказов — они ещё в разработке.
- **Водитель / таксист:** режим доступен лишь при `driver_registrations.review_status='approved'`. Подать анкету может обычный зарегистрированный житель, но работать до проверки нельзя. Реальные пассажирские заказы пока не подключены.
- **Совмещение:** одобренные бизнес и водитель могут быть доступны одновременно; выбор режима не меняет права и статус регистрации.
- **Права администратора/архитектора** — отдельные серверные разрешения, не доступны через пользовательское меню.

## Как работает переключение

В каждом из трёх модулей после входа есть «Настройки · Режим DAapp» → «Сменить режим». Список формируется из результата защищённого SQL RPC `daapp_mode_status()`, а не из поля `goal`, введённого человеком при регистрации.

Нажатие режима вызывает `daapp_set_last_mode(mode)`. SQL ещё раз проверяет права и сохраняет выбранный режим. После успеха открывается соответствующий модуль. Если допуск отозван, сервер отклонит запрос и приложение оставит пользователя на текущем экране.

Отсутствующий бизнес/водитель показывается не как доступный рабочий режим, а как приглашение **оформить заявку**. Пока заявка на проверке, показывается её статус, но кнопки входа в режим нет. Если администратор отзовёт водительский статус, он исчезнет из списка, а при следующем входе система выберет безопасный базовый режим. При блокировке основного аккаунта режимы недоступны, а водитель принудительно снимается с линии.

В любом режиме есть ссылка «Мой профиль, аватар и настройки телефона» на `/account-app/?manage=1`. Параметр `manage=1` отключает автоматический переход, чтобы пользователь мог изменить фото или настройки.

### Технический маршрут

```text
https://antondatsagolov.github.io/DAapp/
  -> account-app (единый вход или восстановленная сессия)
    -> Supabase Auth (проверить пользователя)
    -> daapp_mode_status() (допущенные режимы, последний режим)
       -> last_mode разрешён: открыть этот модуль
       -> last_mode отозван: открыть режим жителя
       -> нет подтверждённого аккаунта: статус регистрации
  Внутри модуля: Настройки -> Сменить режим
    -> daapp_set_last_mode(mode) (проверка на сервере)
       -> сохранить в Postgres -> перейти в модуль
```

## Настройка в Supabase — обязательна

**GitHub Pages публикует интерфейс, но не выполняет SQL автоматически.** Перед живым тестом убедитесь, что выполнены миграции 001–010. Затем в Supabase SQL Editor **ОДИН РАЗ** выполните:

[SQL 011 — unified mode navigation](../supabase/migrations/011_unified_mode_navigation.sql)

SQL 011 создаёт приватное предпочтение последнего режима и две защищённые функции. Новые права пользователя никто не назначает через браузер. Скрипт также запрещает заблокированным аккаунтам менять статус водительской линии.

Для авторизации:
- Supabase Email Provider и Confirm Email включены;
- Redirect URL для `/account-app/` разрешён;
- вход по e-mail+паролю работает с Supabase Auth; вход именно по текстовому логину требует развернуть Edge Function `daapp-username-login` (не автоматически вместе с Pages);
- SMS-провайдер не нужен, телефон остаётся контактным и показывается только при явном согласии взрослого пользователя.

## Тест перед приглашением жителей

1. Зарегистрируйте тестового жителя, подтвердите e-mail, откройте единую ссылку — откроется режим жителя.
2. Подайте тестовую анкету водителя, проверьте, что режим водителя пока **не** появился в списке.
3. Одобрите водителя в админ-панели. В профиле нажмите «Сменить режим → Водитель».
4. Закройте страницу, откройте одну ссылку DAapp ещё раз. Должен открыться водительский кабинет.
5. Создайте и одобрите тестовую организацию. Теперь доступны три режима.
6. Выберите «Предприниматель», перезагрузите браузер и вновь откройте общий адрес. Он должен вернуть в бизнес-модуль.
7. Под административным аккаунтом в тестовой базе приостановите доступ тестового водителя. При новом входе должен восстановиться режим жителя; водитель не должен выходить на линию.

CI тестирует эти правила на **изолированном PostgreSQL** и проверяет клиентскую маршрутизацию. Это не подтверждает, что SQL 011 уже установлен в рабочем Supabase или что пользователь реально получил письмо. Для живого запуска необходим тест реального аккаунта.

Важно: исходные статические ссылки отдельных модулей физически существуют, но сами по себе **не выдают** роли. Важные действия защищаются серверными ограничениями Supabase. Рабочий водитель/бизнес нельзя получить лишь вводом адреса модуля в браузере.
