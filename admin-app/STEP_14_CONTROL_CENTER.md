# DAapp: этап 14 — регистрация и панель администратора/архитектора

## 1. Правильный алгоритм регистрации

**Один человек = один аккаунт**, один Supabase Auth ID. В обычной регистрации он вводит логин, e-mail, пароль, номер для связи, возраст и аватарку (загрузка после подтверждения e-mail). Отдельно выбирает, живёт ли он в Шиели или является гостем, и **с чего хочет начать**: заказы/обзор, бизнес или работа водителем.

1. **Житель / гость**: подтверждает e-mail один раз и **автоматически получает базовый доступ** к карте, личному профилю, контактам с согласия владельцев и другим реализованным сервисам. Не ждёт администратора. Номер телефона пока не подтверждается SMS; никогда не публикуется без отдельного согласия взрослого пользователя.
2. **Предприниматель**: после обычной регистрации получает базовые права жителя/гостя и переходит в business-app. Указывает категорию, организацию, адрес, контакт. Администратор отдельно проверяет и публикует организацию. Товары/услуги, фотографии, складские остатки и заказы нужно реализовать отдельным этапом — пока это **не готово**.
3. **Водитель / таксист**: после обычной регистрации получает базовые права жителя/гостя и переходит в driver-app. В текущей анкете есть тип транспорта, марка/модель, госномер, контактные данные. Год выпуска, фотографии, подтверждение водительских документов и алгоритмы заказов — **ещё не подключены**. Администратор отдельно проверяет и допускает водителя к линии.
4. **Совмещение**: пользователь может одновременно быть жителем, водителем и владельцем бизнеса — переходы между разделами не создают новые Auth-аккаунты.
5. **Вход после регистрации**: e-mail + пароль, без постоянных писем. Логин + пароль через защищённую Edge Function после её развёртывания. Для восстановления пароля e-mail останется нужен.

Выбор первоначального сценария хранится в `daapp_account_applications.onboarding_goal` и **не даёт дополнительных прав**. Авторизация защищена RLS в Supabase. Если Confirm Email в Supabase включён, письмо требуется **один раз при регистрации**, а не каждый вход.

## 2. Что изменено в SQL 010

Новая миграция `supabase/migrations/010_member_self_service_admin_control.sql` применяется строго **после 009** (и всех предыдущих требуемых миграций 001–007). Она:

- включает автоматическое одобрение полноценно заполненных аккаунтов после подтверждения e-mail, а также ранее подтверждённых обычных заявок `pending`; заявки с `rejected` не меняются;
- не даёт обходить регистрацию: аккаунт без логина, контактного телефона и статуса жителя/гостя остаётся `pending`;
- оставляет бизнес и водительские заявки под отдельной модерацией;
- добавляет статистику `daapp_admin_dashboard()`, серверный реестр `daapp_admin_member_register()` и журнал действий;
- даёт архитектору переключатели автоматического допуска и каталога контактов, право блокировать/восстанавливать **неадминистраторские** аккаунты с обязательной причиной;
- защищает все эти операции правами в SQL: кнопки в HTML сами по себе не выдают полномочий.

Внимание: **SQL 010 не применяется автоматически при публикации GitHub Pages**. Выполнение нужно отдельно в Supabase SQL Editor.

## 3. Администратор: без постоянной ссылки из письма

Админ-панель: https://antondatsagolov.github.io/DAapp/admin-app/

Раньше она использовала Magic Link. **Никакой e-mail администратора в коде не прописывался**: вход выполнялся на адрес, указанный самим владельцем аккаунта. Админом считается только Auth-пользователь, чей ID явно присутствует в таблице `public.daapp_admins`.

Теперь:
- если у админ-аккаунта уже есть пароль, достаточно **e-mail + пароль**, письмо не отправляется;
- если раньше был только вход по письму, укажите свой e-mail и нажмите **«Получить ссылку для первого входа»**. После входа в админ-панель откройте **«Безопасный вход без постоянных писем»** и установите пароль (не менее 12 символов);
- впоследствии используйте e-mail и пароль. По требованиям Supabase изменение пароля может потребовать повторной проверки текущей сессии;
- новый аккаунт админа через форму входа не создаётся.

## 4. Панель архитектора

Администратору доступны:
- сводка: количество аккаунтов, активных, ожидающих, заблокированных, регистраций за 7 дней;
- анкеты водителей и активность линии, заявки бизнеса и опубликованные точки карты;
- поиск по пользователям (логин/e-mail/телефон), фильтр статуса, пагинация, подтверждение почты, тип житель/гость, первоначальный сценарий;
- модерация водителей и организаций, диагностика подключений.

**Архитектор** — дополнительный особо доверенный уровень поверх `daapp_admins`. В отличие от обычного администратора, может:
- включать/выключать автоматическое открытие базового доступа после подтверждения e-mail;
- включать/выключать справочник номеров, которые владельцы согласились публиковать;
- блокировать и восстанавливать обычных пользователей (кроме себя и других администраторов), указав причину;
- просматривать журнал таких действий.

Архитектор **не получает сервисный ключ Supabase в браузере, не может удалить базу через интерфейс, не может назначить себе полномочия через браузер**. Настоящий «режим бога» с произвольным доступом к SQL и секретам из публичной веб-страницы опасен.

### Однократное назначение архитектора

Убедитесь, что входите в admin-app под своим настоящим подтверждённым аккаунтом администратора. Выполните **в Supabase SQL Editor**, после SQL 010, подставив реальный e-mail вашего действующего администратора вместо шаблона:

```sql
insert into public.daapp_architects(user_id)
select a.user_id
from public.daapp_admins a
join auth.users u on u.id=a.user_id
where u.email = 'YOUR_EXISTING_ADMIN_EMAIL'
on conflict(user_id) do nothing;
```

Это не создаёт нового пользователя и не выдаёт права кому-либо вне `daapp_admins`. После этого обновите страницу админки.

## 5. Что понадобится сделать вручную в Supabase

1. Проверить миграции 001–009; применить SQL 010 один раз.
2. Authentication → Providers → Email: Enable Email и Confirm Email включены. Allow new users to sign up = ON.
3. Authentication → URL Configuration: `https://antondatsagolov.github.io/DAapp/account-app/` в Redirect URLs.
4. При необходимости отдельного логина вместо e-mail развернуть `supabase/functions/daapp-username-login/index.ts`. Он уже проверяет административное состояние аккаунта и пароль через Supabase Auth; при отключённой функции доступен вход по e-mail и паролю.
5. Установить пароль для уже существующего администратора через однократный Magic Link.
6. Назначить самому себе уровень архитектора SQL-выражением выше. Никому не передавать сервисный ключ.

**Ограничение:** без настройки реальной почтовой доставки на нового пользователя тестовая регистрация может не завершаться. Встроенный отправитель Supabase имеет лимиты; до выхода на широкую аудиторию настройте SMTP, CAPTCHA и ограничения запросов. SQL и CI в GitHub не подтверждают реальную доставку писем.

## 6. Проверка сценария на практике

- Зарегистрировать нового тестового жителя с подтверждением e-mail. После ссылки проверить, что обычный профиль сразу доступен без ручной модерации.
- Зарегистрировать пользователя с первоначальным выбором «Водитель». Убедиться: обычный профиль доступен, но водительская линия — **только после отдельного одобрения анкеты**.
- Аналогично для бизнеса: обычный профиль доступен, публикация организации — **только после проверки**.
- Войти в admin-app без письма, используя e-mail+пароль, и увидеть серверную сводку.
- От имени архитектора временно закрыть справочник и вернуть настройку, проверить журнал; для блокировок использовать только тестовый пользовательский аккаунт.
