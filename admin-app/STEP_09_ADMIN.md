# DAapp — шаг 9: административная модерация организаций Шиели

**Административный интерфейс:** https://antondatsagolov.github.io/DAapp/admin-app/

## Что уже реализовано

- Вход по e-mail (Supabase Auth) и отдельная проверка членства в `public.daapp_admins`.
- Очередь до 100 **ожидающих проверки** заявок. Контакты заявителей видит только разрешённый администратор.
- Просмотр названия, категории, адреса, контакта и координат **из заявки**. Координаты, указанные заявителем, считаются неподтверждёнными.
- Одобрение: администратор подтверждает проверку организации и **вручную** вводит проверенную широту и долготу. Только тогда одна транзакция создаёт опубликованную точку `map_places` и обновляет статус заявки.
- Опциональный публичный телефон; не копируется из заявки автоматически. Перед его публикацией требуется отдельное подтверждение согласия.
- Отклонение заявки без добавления точки на карту.
- Журнал решений `daapp_moderation_log` только для доверенного администратора базы.
- Сервер блокирует повторное одобрение/отклонение одной обработанной заявки (`SELECT ... FOR UPDATE` и проверка статуса `pending`).

## 1. Один раз установить базовую схему

Должны быть уже установлены миграции 004 (`map_places`) и 005 (`place_submissions`). Если пользователь ранее написал, что SQL 004/005 выполнены, **не запускайте их повторно**.

В Supabase Dashboard → SQL Editor выполните **только новую**:

`supabase/migrations/006_shieli_admin_moderation.sql`

Перед запуском проверьте, что имён `daapp_admins`, `daapp_moderation_log` и соответствующих функций ещё нет. Миграция проверяет их и остановится без изменений, если объекты уже существуют. Никаких пользователей она не добавляет в администраторы автоматически.

## 2. Один раз выдать доступ собственному аккаунту

Сначала **вручную проверьте** свой аккаунт в Supabase SQL Editor:

```sql
-- Замените YOUR_EMAIL на ТОЧНЫЙ e-mail входа в DAapp.
select id, email
from auth.users
where lower(email) = lower('YOUR_EMAIL');
```

Должна вернуться ровно одна строка — тот аккаунт, которому вы сознательно разрешаете модерацию.

После проверки скопируйте его UUID и выполните:

```sql
insert into public.daapp_admins(user_id)
values ('00000000-0000-4000-8000-000000000000')
on conflict (user_id) do nothing;
```

**Замените пример UUID на UUID своего проверенного аккаунта.** Не выдавайте доступ целиком роли `authenticated`, не добавляйте всех пользователей и не меняйте поле `profiles.role`.

Проверить текущий список администраторов можно в SQL Editor:

```sql
select a.user_id, u.email
from public.daapp_admins a
join auth.users u on u.id=a.user_id
order by a.assigned_at;
```

Если нужно отозвать доступ, удалите **конкретный** `user_id` из `daapp_admins` через SQL Editor. Не публикуйте эту таблицу как общий список пользователей.

## 3. Разрешить вход

В Supabase → Authentication → URL Configuration → **Redirect URLs** добавьте:

`https://antondatsagolov.github.io/DAapp/admin-app/`

Это не заменяет и не удаляет ранее добавленные URL приложений жителей/предпринимателей.

## 4. Рабочий процесс

1. Откройте https://antondatsagolov.github.io/DAapp/admin-app/ и войдите под разрешённым аккаунтом.
2. Выберите заявку, проверьте право заявителя представлять компанию, адрес и точное местоположение.
3. **Если данные подтверждены:** введите точную проверенную широту/долготу, подтвердите проверку и нажмите **«Одобрить и опубликовать»**. Точка сразу появится на карте жителей после обновления страницы. Если хотите опубликовать номер телефона, нужно отдельно проверить согласие владельца.
4. **Если данные не подтверждены:** нажмите **«Отклонить заявку»**.

## Границы безопасности

- **Никаких секретных ключей** в GitHub, HTML или JS. Функции вызываются от имени вошедшего пользователя с обычным publishable key.
- Проверка администратора осуществляется **на сервере при каждом RPC** с `auth.uid()` и `daapp_admins`; наличие кнопок в браузере ничего не разрешает.
- `security definer` функции имеют `search_path=''` и явно заданные имена таблиц. Доступ к ним имеет только `authenticated`, с дополнительной проверкой списка администраторов.
- `anon` и обычные авторизованные пользователи не могут читать общую очередь, менять статусы, видеть чужие номера телефонов или публиковать точки.
- Публикация требует **новые проверенные координаты**, а не те, которые ввёл заявитель.
- Функция пишет журнал решений, а операции по одной заявке выполняются атомарно.
- В интерфейсе все данные заявок показываются как текст, а не HTML.
- Эта миграция **не создаёт администратора автоматически** и не меняет RLS `profiles`, `place_submissions` или `map_places`.

## Ограничения текущей версии

- Администратор назначается вручную через SQL Editor.
- Нет редактирования опубликованной карточки, отката решения через UI и комментария об отказе. Для исправлений нужен отдельный будущий механизм.
- Нет проверки документов или юридического подтверждения автоматически; это обязанность администратора.
- Live-проверка RPC и реальной базы возможна только после выполнения SQL 006 и назначения администратора. Автоматические тесты GitHub не создают реальных пользователей/точек.
